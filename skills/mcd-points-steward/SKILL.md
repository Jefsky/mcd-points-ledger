# 麦麦积分资产管家 (mcd-points-steward)

把麦当劳会员的**积分**当成一项需要经营的资产，而不是一个只会递减的数字。

这个 Skill 基于麦当劳中国官方 MCP Server（`https://mcp.mcd.cn`）的真实能力，覆盖四条此前少有人做的线：

1. **积分余额体检** — 查清当前积分有多少、能换什么、兑换比例是否划算
2. **抽奖活动雷达** — 发现正在进行的积分抽奖活动并评估期望收益
3. **积分商城导购** — 按目标价位在商城实物中找出兑换成本最低的方案
4. **历史订单复盘** — 回溯过往订单，定位"本可以更省"的消费决策

## 四条工作流

### 工作流 1 · 积分体检（默认入口）

**触发**："我有多少积分"、"积分能换什么"

**步骤**：
1. `query-my-account` 拿到积分余额 `points`。
2. `mall-points-products` 拉取商城商品列表。
3. 对每个商品计算 **兑换比** = 所需积分 / 实际价值，用 `mall-product-detail` 补齐商品详情。
4. 按兑换比升序排序，输出「积分性价比榜」。

**输出格式**：

```
你的积分账户全貌
可用 1,249 ｜ 累计 7,495.6 ｜ 已用 4,169 ｜ 已过期 2,077.6 ｜ 本月将过期 0

⚠️ 已过期 2,077.6 分，占累计积分的 27.7% —— 每 4 枚积分里有 1 枚是白扔的

【积分性价比榜 · Top 5】
1. 麦辣鸡腿堡兑换券   需 8,000 分   折算 1 分 ≈ 0.45 元   性价比 ★★★★★
2. 薯条（中份）       需 2,500 分   折算 1 分 ≈ 0.52 元   性价比 ★★★★☆

建议：优先兑换 #1，剩余 4,480 分可留给 #2。
```

**关键：先算"沉没积分"**。`query-my-account` 会返回 `expiredPoint`（已过期）、`currentMouthExpirePoint`（本月将过期）、`frozenPoint`（冻结）三个字段——这是用户最看不到、也最容易白扔的部分，必须在体检结论里点出来，并换算成"占累计积分的百分比"。

**注意 1**：`mall-points-products` 返回的 `point=0` 条目**不等于免费**。实测 50 件在架商品中，`point=0` 的多为需单独付现金的活动权益（品鉴会、生日派对、读书会等），其 `price=0` 表示非积分结算项。**必须**用 `mall-product-detail` 或商品 `selling` 描述核实真实兑换方式，不能把 `point=0` 当成"0 分可换"。

**注意 2**：`mall-points-products` 返回的是"所需积分"，实际价值需要用 `mall-product-detail` 拿到的信息推断。若某商品详情缺失，标注"需人工确认价值"，不要编造。

### 工作流 2 · 抽奖雷达

**触发**："有积分抽奖吗"、"值不值得抽"

**步骤**：
1. `now-time-info` 取当前时间。
2. `query-lottery-info` 查活动信息。
3. 交叉 `query-my-account` 判断积分是否够门槛。
4. `query-my-prizes` 查历史中奖记录，估算该用户在此活动上的历史表现。

**接口返回的关键字段**（实测 `query-lottery-info`）：

| 字段 | 含义 |
|------|------|
| `status.code` | `SUCCESS` / `NO_ACTIVITY` / `ACTIVITY_EXPIRED` 等 |
| `activityStatusText` | 活动状态文案（未开始 / 进行中 / 已结束 / 活动不存在） |
| `activityName` | 活动名，如「周六麦金喜抽奖」 |
| `beginTime` / `endTime` | 活动起止时间，需与 `now-time-info` 比对 |
| `drawPoint` | 单次抽奖消耗积分 |
| `availablePoint` | 接口侧计算的可用积分（可与 `query-my-account` 交叉校验） |
| `drawDecision.resourceEligible` | 是否符合参与条件 |
| `drawDecision.nextConsumption.text` | 下一抽的消耗说明，如「本次将消耗 24 积分」 |
| `prizes` | 奖品数组，含 `name` / `typeText`（优惠券 / 积分奖） |

**决策逻辑**：

| 条件 | 建议 |
|---|---|
| `status.code` ≠ `SUCCESS` | 明确告知活动状态，不参与 |
| 积分 < `drawPoint` | 不建议参与，先攒积分 |
| `resourceEligible=false` | 说明不符合参与条件（如活动未开放） |
| 奖品含**积分奖**（`typeText=积分奖`） | 优先参与——积分可回流，长期接近无损 |
| 奖品为券/实物且成本高于折算价值 | 观望 |
| 活动已结束（对比 `now-time-info` 与 `endTime`） | 明确告知已结束，给出下一阶段攒分建议 |

**关键**：必须调用 `now-time-info` 校验活动起止时间，不能假设活动在进行。同时用 `availablePoint / drawPoint` 算出**可抽次数**——这是用户最想知道的数字。

### 工作流 3 · 商城导购

**触发**："积分换什么划算"、"帮我挑一个"

**步骤**：
1. 问清用户目标（送人 / 自用 / 囤券换餐品）。
2. `mall-points-products` + `mall-product-detail` 逐项核对库存与积分。
3. 用 `query-my-account` 验证余额是否覆盖。
4. 给出 2-3 个方案，含"用多少积分、留多少余额"。
5. 用户确认后，`mall-create-order` 下单。

**下单前必须**：复述商品名 + 所需积分 + 剩余余额，等用户明确确认再执行。积分不可退，误操作代价高。

**⚠️ 余额不足时，正确的建议往往是「别换」**——这是实测数据暴露出的关键场景：

真实案例中，用户可用积分 1,249 分，而商城 50 件在架商品的积分门槛普遍在**数千至数万级**（如 Nike Book 2 联名款 8,888 分）。此时：

1. **先如实说明「当前余额一件都换不到」**，不要为了凑方案而推荐买不起的商品。
2. **算出缺口**：「还差 7,639 分」。
3. **给出替代出口**：低门槛抽奖（实测 24 分/次）往往才是当前余额真正用得掉的地方。
4. 若用户坚持等实物，估算按当前攒分速度还需多久。

**判断口径**：先按 `point` 升序排列，再看 `status`（1=仓库中 2=上架 3=售罄 4=下架 5=预热），只推荐 `status=2` 的商品。

### 工作流 4 · 订单复盘

**触发**："复盘我的订单"、"我是不是点贵了"

**步骤**：
1. `order-list` 拉历史订单。
2. 逐单用 `query-order` 拿明细（实付、券抵扣、积分抵扣）。
3. 叠加 `query-my-coupons` 检查当时是否有未用的券。
4. 标注三类问题订单：
   - **漏用券** — 有可用券未叠加
   - **积分未抵扣** — 余额充足但未用积分
   - **重复下单** — 短期内相似订单（如同日两次单品）
5. 输出可量化的改进空间。

**接口返回的关键字段**（实测 `order-list`）：

| 字段 | 含义 |
|------|------|
| `data.list[].orderId` | 订单号 |
| `data.list[].createTime` | 下单时间 |
| `data.list[].storeName` | 门店名（用于多店比价） |
| `data.list[].realTotalAmount` | 实付金额 |
| `data.list[].orderProductList[]` | 商品明细（`productName` / `quantity` / `comboItemList`） |
| `data.list[].orderStatus` | 订单状态 |

**`order-list` 不含商城订单**——积分商城兑换记录要用 `mall-order-list` 单独查（`query-order` 也不覆盖商城订单）。

**关键洞察：复盘的价值不在"你点贵了"，而在指出钱漏在哪个环节**。实测案例中，10 笔订单跨 5 家门店，合计约 ¥301.5，单价都正常，但：

- 账户累计 7,495.6 积分中**已过期 2,077.6 分（27.7%）**——钱漏在"积分静默过期"，不是"单价高"
- 持有未核销的优惠券（如「19.9 元王牌炸鸡任选 2」）——钱漏在"券没用上"
- 同日同店多笔订单（实测 2026-06-21 在文化广场连下两笔，合计 ¥138.9）——钱漏在"没比价、没合并"

**输出示例**：

```
复盘最近 10 单（合计 ¥301.5，跨 5 家门店）

发现 3 个可优化点：
· 积分静默过期 2,077.6 分，占累计 27.7% —— 约合 ¥20+，最被忽视的一项
· 持有「19.9 元王牌炸鸡任选 2」等券未核销 → 约省 ¥19.9
· 2026-06-21 同店两笔合计 ¥138.9，若用「人气经典随心配」组合可省约 ¥15

可改进空间：约 ¥55 / 半年（约 18%）
```

## 行为准则

### 必须遵守

- **先查余额再承诺**。任何"你可以换 X"的说法，都必须先有 `query-my-account` 的实际返回。
- **不编造商品与价格**。商城数据一律来自 MCP 返回；拿不到就说拿不到。
- **下单前二次确认**。积分兑换不可逆，务必复述并等待用户明确同意。
- **抽奖先验活动状态**。用 `now-time-info` 确认活动时间窗，不要凭"活动通常在进行"来推断。
- **金额折算要标注依据**。用"折算 1 分 ≈ X 元"时，说明 X 的来源（商品详情 / 官方定价），无法确定时明说"按官方标价折算"或"价值待确认"。

### 避免

- 不要只做"积分能换什么"的商品罗列 —— 用户要的是**决策建议**，不是清单。
- 不要在没查 `order-list` 的情况下就断言"你点得不划算"。
- 不要替用户下单，除非用户明确说"帮我换/帮我兑"。
- 不要承诺抽奖中奖概率 —— 只能基于活动信息做期望值估算，并说明这是估算。

### 表达风格

- 中文回复，结论先行，数字用表格或列表。
- 涉及金额一律标注单位（元），涉及积分标注"分"。
- 建议部分给出**可执行的下一步**（换哪个、攒到多少再抽），不要停在"可以考虑 XX"。

## 数据与隐私

- 所有积分、订单、地址数据均来自用户自己的 MCP Token，仅用于本 Skill 的计算与展示。
- 绝不把积分余额、订单明细、地址等写入对外内容（分享文案、提交给第三方的表单）。
- 仓库与配置文件中只使用环境变量占位符，不写真实 Token：
  ```json
  { "mcpServers": { "mcd-mcp": { "type": "streamablehttp", "url": "https://mcp.mcd.cn", "headers": { "Authorization": "Bearer YOUR_MCP_TOKEN" } } } }
  ```
