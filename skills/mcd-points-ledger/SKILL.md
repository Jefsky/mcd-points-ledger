# 麦麦积分真账本 (mcd-points-ledger)

**它标称有多少，你算的是还剩多少、能不能真换到。**

麦当劳官方接口报「有 50 件商品可兑换」，但实测真正能换到的只有 9 件——而且这 9 件**全部需要另付现金**。这个 Skill 做的是**把接口标称的表面值还原成实际可执行的口径**：先验真，再算账，最后才建议。

---

## 何时使用

| 用户意图 | 触发示例 |
|---|---|
| 商城验真 | "商城里到底有什么能换"、"有没有已经下架的" |
| 现金成本核算 | "兑换是不是还要另外花钱"、"这个划不划算" |
| 积分净值 | "我这些积分实际值多少"、"过期了多少" |
| 抽奖回本 | "我能抽多少次"、"抽奖划算吗" |
| 积分有效期 | "我的积分什么时候过期"、"会不会白扔" |

## 工具依赖（全部来自麦当劳官方 MCP Server）

| 工具 | 用途 | 验真价值 |
|---|---|---|
| `mall-points-products` | 列出积分商城商品 | **必须带 `catRuleIds` 全量查**，否则漏报 |
| `mall-product-detail` | 单商品详情 | **读取 `extTradePrice` 的入口**（列表接口不提供）→ 隐藏现金成本 |
| `query-my-account` | 积分余额 | 提供 `expiredPoint` 等沉没字段 |
| `query-lottery-info` | 抽奖活动信息 | 提供 `drawPoint` → 可抽次数 |
| `query-my-prizes` | 中奖记录 | 抽奖收益基线 |
| `draw-lottery` | 参与抽奖 | 有副作用，需确认 |
| `mall-create-order` | 积分兑换下单 | 有副作用，需二次确认 |
| `mall-order-list` | 商城订单流水 | 兑换历史追踪 |
| `order-list` / `query-order` | 餐饮订单 | 复盘，不含商城订单 |
| `query-my-coupons` | 我的优惠券 | 漏用券检测 |
| `now-time-info` | 当前时间 | 校验活动与兑换窗口 |

## 五条工作流

### 工作流 1 · 货架验真（核心入口）

**触发**："商城里能换什么"、"有没有下架的"

这是整个 Skill 的主线。**在给出任何兑换建议之前，必须先跑完这一步。**

**步骤**：

1. **默认查询** `mall-points-products`（不带参数）→ 记录返回件数作为"接口标称口径"。
2. **全量查询**：遍历分类规则 `catRuleIds` 取并集去重 → 得到真实件数。
   ```python
   CAT_RULE_IDS = ['1>4','2','2>8','2>9','1>6>20','1>6>21','1>6>22','1>6>25','1>6>34','1>6>40']
   ```
   实测：默认返回 50 件，全量去重后 54 件，**默认漏报 4 件**。
3. **筛出积分结算项**：`point > 0`。`point=0` 是需另付现金的活动权益（品鉴会、生日派对），**不是免费**。
4. **过期未下架检测**：对 `status == 2`（上架）的商品，比较 `downTime` 与当前时间。`downTime` 已过却仍标上架 = **过期未下架**。
   实测：27 件标上架的积分商品中，**18 件（66%）是过期未下架**。
5. **隐藏现金成本**：对真正可兑的商品逐个调 `mall-product-detail`，读 `skuList[].extTradePrice`。
   实测：9 件真正可兑商品中，**9 件全部需另付现金，纯积分可兑 0 件**。
6. **同名多 spuId**：按 `spuName` 分组，同名挂着不同积分的即为陷阱。
   实测：「10.9元指定小食任选」同时存在 100 分（spuId 17076）与 200 分（spuId 17077）两个条目。

**输出格式**：

```
积分商城货架验真结果

官方接口报告在架     : 50 件
全量去重后           : 54 件（默认查询漏报 4 件）
其中积分结算项       : 27 件
标为上架但窗口已关闭 : 18 件 (66%)  ← 过期未下架
真正可兑             : 9 件
  其中需另付现金     : 9 件        ← 隐藏现金成本
  纯积分可兑         : 0 件

真正可兑清单（9 件，全部需另付现金）：
· 3.9元圆筒冰淇淋        100 分  + 另付 ¥3.9
· 6.9元可乐麦炫酷         50 分  + 另付 ¥6.9
· 10.9元指定小食任选     100 分  + 另付 ¥10.9   ← 同名另有 200 分版本，勿选错
· 10.9元指定小食任选     200 分  + 另付 ¥10.9
· 16.9元2份麦辣鸡翅     200 分  + 另付 ¥16.9
· 16.9元麦辣可乐组合     500 分  + 另付 ¥16.9
· 17.9元板烧可乐组合     500 分  + 另付 ¥17.9
· 21.9元巨无霸可乐组合   800 分  + 另付 ¥21.9

结论：接口标称的 50 件中，逐件核对后有 9 件当前可换，且都需要另付现金。
     若你的积分不足 100 分，当前商城实际上无可纯积分兑换的商品。
```

**关键**：`downTime` 已过但 `status` 仍是 2，是这个商城接口最隐蔽的坑。**必须逐件核对时间窗口，不能只信 `status` 字段。**

### 工作流 2 · 净值核算

**触发**："我这些积分实际值多少"、"过期了多少"

**步骤**：
1. `query-my-account` 拿五项口径。
2. 算**沉没率** = `expiredPoint` / `accumulativePoint`。
3. 结合工作流 1 的真可兑清单，算**可达净值** = 真正可兑商品的 `point` 门槛之和 vs 你的余额。

**输出示例**（真实账户）：

```
你的积分账户全貌
可用 1,331.3 ｜ 累计 7,577.9 ｜ 已用 4,169 ｜ 已过期 2,077.6 ｜ 本月将过期 0

⚠️ 已过期 2,077.6 分，占累计积分的 27.4% —— 每 4 枚积分里有 1 枚是白扔的

可达净值：真正可兑商品最低门槛 50 分，你的 1,331.3 分足够
         但 9 件全部需另付现金，纯积分可兑 0 件
```

**关键**：`expiredPoint` / `currentMouthExpirePoint` / `frozenPoint` 是用户最看不到、也最容易白扔的部分，**必须第一个点出来**，并换算成占累计积分的百分比。

### 工作流 3 · 抽奖回本率

**触发**："我能抽几次"、"抽奖划算吗"

**步骤**：
1. `now-time-info` 取当前时间。
2. `query-lottery-info` 查活动，**必须校验 `beginTime`/`endTime` 是否在窗口内**。
3. 算**可抽次数** = `availablePoint` // `drawPoint`。
4. 读 `prizes[].typeText`：含「积分奖」意味着积分可回流。
5. `query-my-prizes` 查历史中奖做基线。

**实测字段**：

| 字段 | 含义 |
|---|---|
| `activityStatusText` | 活动状态（进行中 / 已结束 / 未开始） |
| `drawPoint` | 单次消耗（实测 24 分） |
| `drawDecision.resourceEligible` | 是否符合参与条件 |
| `drawDecision.nextConsumption.text` | 下一抽消耗说明 |
| `prizes[].typeText` | 奖品类型（优惠券 / 积分奖） |

**输出示例**：

```
抽奖回本核算
活动「周六麦金喜抽奖」 · 进行中（2025-09-06 ~ 2030-12-31）
单次消耗 24 分 ｜ 可用 1,331.3 分 ｜ 可抽 55 次
奖品池含积分奖 → 积分可回流，长期接近无损

建议：当前商城纯积分可兑为 0，抽奖是当时更现实的一条出口。
```

**决策表**：

| 条件 | 建议 |
|---|---|
| `status.code` ≠ `SUCCESS` | 明确告知活动状态，不参与 |
| 积分 < `drawPoint` | 不建议参与，先攒积分 |
| `resourceEligible=false` | 说明不符合参与条件 |
| 奖品含**积分奖** | 优先参与，积分可回流 |
| 奖品仅券/实物且成本高于折算 | 观望 |
| 已结束（对比 `now-time-info` 与 `endTime`） | 明确告知，给出攒分建议 |

**关键**：不要假设活动在进行中，也不要只算次数不给回本判断。

### 工作流 4 · 兑换决策

**触发**："帮我换 X"

**步骤**：
1. **先跑工作流 1**，拿到真可兑清单。
2. 问清用户目标（送人 / 自用 / 囤券）。
3. 核对库存与积分门槛。
4. 用 `query-my-account` 验证余额覆盖。
5. **明确报出另付现金金额**（来自 `extTradePrice`）。
6. 用户确认后，`mall-create-order` 下单。

**下单前必须复述三件事**：商品名 + 所需积分 + **另付现金金额**，等用户明确确认。

**⚠️ 余额不足时，正确的建议往往是「别换」**：

实测案例中，可用 1,331.3 分，而真正可兑商品的最低门槛是 50 分——看似够用。但：
1. 若要看中 200 分以上的商品，余额不够。
2. 9 件全部需另付现金，积分只是门槛券，**不是全额支付**。
3. 若 `point=0` 类活动权益被误当作免费，会导致完全错误的决策。

**判断口径**：只推荐 `status=2` **且 `downTime` 未过** **且** `extTradePrice` 已明确告知的商品。

### 工作流 5 · 订单复盘

**触发**："复盘我的订单"、"我是不是点贵了"

**步骤**：
1. `order-list` 拉历史订单。
2. 逐单 `query-order` 拿明细。
3. 叠加 `query-my-coupons` 检查未用券。
4. 标注三类问题：漏用券 / 积分未抵扣 / 重复下单。
5. 输出可量化的改进空间。

**接口返回的关键字段**（实测 `order-list`）：

| 字段 | 含义 |
|---|---|
| `data.list[].orderId` | 订单号 |
| `data.list[].createTime` | 下单时间 |
| `data.list[].storeName` | 门店名（多店比价） |
| `data.list[].realTotalAmount` | 实付金额 |
| `data.list[].orderProductList[]` | 商品明细 |
| `data.list[].orderStatus` | 订单状态 |

**`order-list` 不含商城订单** —— 商城兑换记录要用 `mall-order-list` 单独查。

**关键洞察**：复盘的价值不在"你点贵了"，而在指出**钱漏在哪个环节**。实测案例中，10 笔订单跨 6 家门店，合计约 ¥395.9，单价都正常，但：
- 累计 7,577.9 积分中**已过期 2,077.6 分（27.4%）**——钱漏在"积分静默过期"
- 持有未核销的优惠券（如「19.9 元王牌炸鸡任选 2」）——钱漏在"券没用上"
- 同日同店多笔订单（实测 2026-06-21 在文化广场连下两笔，合计 ¥138.9）——钱漏在"没比价、没合并"

## 行为准则

### 必须遵守

- **先验真再建议**。任何"你可以换 X"之前，必须先跑完工作流 1 的五项检测（漏报/过期未下架/现金成本/同名/窗口）。
- **不编造商品与价格**。商城数据一律来自 MCP 返回；拿不到就说拿不到。
- **现金成本必须显式告知**。若 `extTradePrice > 0`，必须在建议中写明另付金额。
- **下单前二次确认**。积分兑换不可逆，务必复述并等待用户明确同意。
- **抽奖先验活动状态**。用 `now-time-info` 确认时间窗，不要凭"活动通常在进行"来推断。
- **金额折算要标注依据**。用"折算 1 分 ≈ X 元"时说明来源，无法确定时明说"价值待确认"。

### 避免

- 不要只做商品罗列 —— 用户要的是**决策建议**，不是清单。
- 不要把 `point=0` 当成"0 分免费"，那是需另付现金的活动权益。
- 不要在没跑验真的情况下说"商城里有 N 件可换"——接口标称口径是 50，真正可兑是 9。
- 不要在没查 `order-list` 的情况下断言"你点得不划算"。
- 不要替用户下单，除非用户明确说"帮我换/帮我兑"。
- 不要承诺抽奖中奖概率 —— 只能基于活动信息做期望值估算，并说明这是估算。

### 表达风格

- 中文回复，结论先行，数字用表格或列表。
- 涉及金额一律标注单位（元），涉及积分标注"分"。
- 建议部分给出**可执行的下一步**，不要停在"可以考虑 XX"。

## 可复现验证

本项目所有数字都可由评审自行复现，无需相信作者的说法：

```bash
export MCD_MCP_TOKEN=你的Token
python scripts/verify_shelf.py
```

脚本会输出漏报件数、过期未下架占比、隐藏现金成本件数、同名 spuId 冲突、可抽次数，与本文档数字完全一致。

## 数据与隐私

- 所有积分、订单、地址数据均来自用户自己的 MCP Token，仅用于本 Skill 的计算与展示。
- 绝不把积分余额、订单明细、地址等写入对外内容（分享文案、提交给第三方的表单）。
- 仓库与配置文件中只使用环境变量占位符，不写真实 Token：
  ```json
  { "mcpServers": { "mcd-mcp": { "type": "streamablehttp", "url": "https://mcp.mcd.cn", "headers": { "Authorization": "Bearer YOUR_MCP_TOKEN" } } } }
  ```
