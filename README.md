## 为什么做这个

大多数积分导购的逻辑是：**接口返回什么，就推荐什么。**

但真实数据打脸了——2026-10-24 抓取麦当劳官方 MCP，商城接口报告 50 件商品，逐件核对后：

```
官方口径 50 件
  ↓ 全量去重（遍历 10 个分类规则）        54 件   ← 默认查询漏报 4 件
  ↓ 筛出积分结算项（point > 0）           27 件   ← point=0 是需另付现金的活动权益
  ↓ 核对每件兑换窗口 downTime            18 件窗口已过  ← 假上架，66%
  ↓ 逐件读 skuList[].extTradePrice       9 件全部带现金  ← 隐藏现金成本
  ↓ 纯积分可兑                           0 件
```

**两个最容易被忽略的坑**：

1. **`status=2`（上架）不代表能换。** 接口状态字段不会随兑换窗口关闭而更新——27 件标着"上架"的积分商品里，18 件的 `downTime` 早已过去。Nike 联名款（8,888 分）、罗技键鼠套装（6,666 分）都属这类，**看状态字段会得到一个不存在的货架**。
2. **`point` 是门槛，不是价格。** 「200 分换 10.9 元小食」的真实语义是「200 分 **+ 另付 10.9 元**」。`extTradePrice` 只在 `mall-product-detail` 里，默认列表接口完全不给。

### 更正一个我自己犯过的错

这个项目最初版本的结论是「1,249 分一件都换不到，商城门槛动辄数千」。

**那是错的**——因为它也信任了 `status` 字段。剔除 18 件假上架后，真正可兑的 9 件门槛只要 50–800 分，**1,249 分全部够得着**。错的不是商品，是"够不着"这个结论本身。

修正后的结论更准确也更有用：**积分在这里是"门槛券"而不是"支付手段"**，真实成本永远是「积分 + 现金」。

这个错能发生，是因为没有把"验真"当成必做的第一步。**所以本项目把验真做成了强制工作流 1，也做成了任何人都能跑的脚本。**

### 还有两个方法论错误，也一并写在这

**其一**：我最初的赛道判断只统计了活动页排行榜**前 12 名**的工具提及率，得出「积分资产运营 0-2/12 稀疏，是蓝海」。全量扫描后真相是 **524/878（59.7%）涉及积分、262/878（29.8%）写着"资产/管家"**。头部项目的提及率根本不能代表赛道密度。

**其二**：我第一次写差异化论证时，样本只有 52 个项目，据此写下「假上架检测 0/52 覆盖」。但**那个和我定位高度重叠的直接竞品，根本不在这 52 个样本里** —— 它是在我抓取之后才加入榜单的。这句话如果留在文档里，就是一个会被评审当场拆穿的假声明。

所以我把全量 1052 个报名仓库重扫了一遍（878 个成功抓取），并在 [docs/coverage-analysis.md](docs/coverage-analysis.md) 里公开了方法论与原始统计口径 —— **包括对我自己错误的记录**。

不传 `catRuleIds` 的默认查询只返回 50 件；遍历 10 个分类规则取并集去重后是 **54 件**。

|---|---|---|
| 9.9元指定小食任选 | 100 | ❌ 假上架 |
| 3.9元圆筒冰淇淋 | 100 | ✅ 可兑（另付 ¥3.9） |
| 16.9元2份麦辣鸡翅 | 200 | ✅ 可兑（另付 ¥16.9） |

其中 **2 件正是门槛最低的真可兑商品**——不校正就直接漏掉了最该推荐的选项。


## 💡 一个可能有用的发现：影子价格对池子口径极度敏感

很多做积分价值计算的项目会算出一个「每积分值多少钱」的数字。这个数字**取决于你把哪些商品算进兑换池**，而这中间藏着一个很隐蔽的分歧：

`mall-points-products` 返回的商品里，`status=2`（上架）但 `downTime` 已过期的占多数。**信不信 `status`，结果差 172%。**

我用同一批真实数据（2026-10-25）实测：

| 口径 | 池子 | 最优效率 | 价值极差 |
|---|---:|---:|---:|
| 信任 `status`（status=2 即认为可兑） | 27 件 | **0.3760 元/积分** | 13.7 倍 |
| 额外要求 `downTime` 未过期 | 9 件 | **0.1380 元/积分** | 5.0 倍 |

**这不是"哪个口径对"，而是"这个数字取决于什么"。**

用它判断「花 500 积分省 24 元到底划不划算」时，无论你选哪个口径，都必须先说清池子是怎么划的 —— 否则结论会系统性偏移 1.7 倍。

`scripts/verify_shadow_price.py` 就是把这件事变成一段任何人都能重跑的检查。

## 安装

### 前置条件

需要申请到麦当劳中国的 MCP Token。前往 [麦当劳 MCP 开放平台](https://open.mcd.cn/mcp)：

1. 右上角【登录】→ **微信扫码**确认登录
2. 点击【控制台】→【激活】申请 MCP Token
3. 阅读并同意服务协议 → 复制 Token

### 方式一 · WorkBuddy（推荐）

1. 打开 WorkBuddy → 左侧【专家·技能·连接器】→【连接器】页签
2. 右上角【自定义连接器】→【配置MCP】
3. 填入以下 JSON，把 `YOUR_MCP_TOKEN` 替换为你的 Token：

```json
{
  "mcpServers": {
    "mcd-mcp": {
      "type": "streamablehttp",
      "url": "https://mcp.mcd.cn",
      "headers": {
        "Authorization": "Bearer YOUR_MCP_TOKEN"
      }
    }
  }
}
```

4. 保存 → 在【自定义连接器】中启用 `mcd-mcp`
5. 把 `skills/mcd-points-ledger/` 放入你的 Skill 目录并启用

### 方式二 · 其他 MCP Client

本 Skill 兼容任何支持 Streamable HTTP 的 MCP Client（Cherry Studio、Cursor、Trae、VS Code 等），配置同上。参考[官方接入文档](https://github.com/M-China/mcd-mcp-server#2-快速开始)。

> 限流：每个 Token 每分钟最多 600 次请求。本 Skill 单次工作流通常在 10 次以内。

## 设计原则

- **先验真再建议** — 任何兑换建议之前，四道检测必须先跑完
- **不编造商品与价格** — 商城数据一律来自 MCP 返回，拿不到就说拿不到
- **现金成本必须显式告知** — `extTradePrice > 0` 就要写明另付金额
- **状态字段不可尽信** — `status` 要和 `downTime` 交叉验证
- **下单前二次确认** — 积分兑换不可逆，务必复述并等待明确同意
- **抽奖先验活动状态** — 用 `now-time-info` 校验时间窗，不凭感觉推断
- **数字可复现** — 每个结论都有脚本能跑出来

## 欢迎来坐坐

这个项目最有价值的部分不是代码，是**那些不太显而易见的接口行为**。如果你也踩过坑，欢迎补充。

**我想请你帮个忙**

如果你用麦当劳积分商城的 MCP 数据做过事，大概率遇到过下面这些情况之一：

- 查出来的商品不少，但用户说"兑换不了" → 多半是 `status=2` 但窗口已关
- 用户说"还要另外付钱" → 多半是 `extTradePrice`，列表接口不给
- 同样的商品查出来两遍 → 多半是没遍历 `catRuleIds`
- 算出来的余额是 0 → 多半是接口返回的是字符串

**这些我都写进 `scripts/verify_shelf.py` 了，直接拿去用：**

```bash
git clone https://github.com/Jefsky/mcd-points-ledger
cd mcd-points-ledger
export MCD_MCP_TOKEN=你的Token
python scripts/verify_shelf.py
```

**如果它帮到了你**，欢迎点个 ⭐ Star —— 这对我真的很重要。

**如果发现了它没覆盖的情况**，请开一个 Issue 告诉我，我会去实测后补进去。这个项目最大的动力就是"有人发现新坑，我把它验真后加进去"。

**如果你在做类似的项目**，欢迎来聊。我扫过活动页全部 1052 个报名仓库的工具覆盖度数据（方法论在 `docs/coverage-analysis.md`），如果你想知道某个工具方向有没有人做过、或者想知道自己项目在做什么方向，可以直接问我，我能给你一份现成的统计。
